# Architecture

Living doc: how the system is *now*. Reasoning lives in [ADRs](adr/), not here.

## Components

- **Web app** (`src/`): a single-page app installed on the phone as a PWA. It talks to Supabase with the public key and the user's login token. Screens: Chat (with a preview of each menu it saved or showed and a button to the Menu tab, and a live shopping list card with its total and a button to the List tab), Menu (the week, Cambiar buttons that hand a draft to the chat, and kcal and macros per meal and per day when the numbers switch is on), List (the saved menu added up into a shopping list by section, with what you have at home crossed out or reduced, each line's product at the store it's bought in, and share or copy; on top, where to buy it by the store rule and whether it fits the menu's budget) and Profile (with the numbers switch).
- **Supabase**: one hosted project.
  - Auth: Google's sign-in button ([ADR 0027](adr/0027-google-sign-in-button.md)), or a magic link email for now and an emailed code from milestone 6.
  - Postgres (`supabase/migrations/`), with row-level security on every table. Users read only their own rows, except the price catalog below. They write only `conversations`, `menus.have` and the profile's `show_numbers` (through `set_show_numbers`); the `chat` function writes the rest ([ADR 0014](adr/0014-client-reads-chat-function-writes.md)):
    - `conversations`: the user's chats, with a title (the first message) and `updated_at` for sorting.
    - `messages`: the turns of each conversation. `content` holds each message exactly as sent to or returned by Claude, thinking blocks included. The history is append-only and replayed as is.
    - `profiles`: what the AI saved about the user (goal, meals, cooking time, nutritionist's plan, and can't eat / don't like / like / want lists) and the numbers switch `show_numbers`, as one `data` JSON object. `set_show_numbers(boolean)`, a security-definer function, lets the browser set that one key ([ADR 0021](adr/0021-numbers-switch-in-the-profile.md)).
    - `menus`: the menu the AI saved, one per user, as one `data` JSON object (recipes, the one to seven days that point at them, the optional `budget` in pesos, and `products`: the `store_sku` picked for each list item at each store, [ADR 0024](adr/0024-agent-builds-the-menu-from-real-products.md)), plus `have`: what the user has at home for the shopping list, written by the List tab and by the `update_shopping_list` tool, kept across menu saves ([ADR 0017](adr/0017-shopping-list-derived-in-the-browser.md)).
  - The price catalog ([ADR 0016](adr/0016-price-catalog-one-row-per-product-per-chain.md)) is readable by any signed-in user, and only the scraper writes it:
    - `stores`: the four chains (Devoto, Géant, Disco, Ta-Ta).
    - `scrape_runs`: one per chain per scraper run, with the branch or sales channel its prices belong to (`price_context`) and counters.
    - `store_products`: one row per product per chain, with the latest price, the package size (for items sold by weight, the unit of sale: [ADR 0023](adr/0023-scraper-prices-for-the-unit-of-sale.md)), `unit_price` (per kg, liter or unit) and `checked_at`.
    - `price_changes`: each price a product has had, written by a trigger when a product is first read and when its price changes.
    - `upsert_store_products(rows)`: the scraper's only way to write, callable only with a secret key. It holds the merge rules.
    - `search_products(q, lim)`: the chat agent's product search over Disco, Géant and Ta-Ta. Spanish full-text search without accents plus trigram similarity, with the caller's own permissions ([ADR 0024](adr/0024-agent-builds-the-menu-from-real-products.md)).
  - Edge Function `chat` (`supabase/functions/chat/`): checks the caller's token, loads that conversation's history, adds the saved profile and menu to the new message when they changed ([ADR 0011](adr/0011-profile-in-each-chat.md), [ADR 0013](adr/0013-menu-saved-by-a-chat-tool.md)), calls Claude (up to 6 calls per turn, the last ones without tools after 100 s), streams the reply as plain text, runs the `search_products` (reads `store_products`), `save_profile`, `save_menu` (checks the picked products and answers with the price), `show_menu` (writes nothing), `update_shopping_list` and `show_shopping_list` (writes nothing) tools, adds the price and the list as numbers to the last list tool's result in each round ([ADR 0022](adr/0022-list-follows-the-menu.md), [ADR 0024](adr/0024-agent-builds-the-menu-from-real-products.md)), logs each call's tokens and time, and stores the whole exchange at the end. Reads run as the user, under row-level security. Writes use the service-role key and name the user's id from the verified token. After 100 user turns in 24 hours it answers 429 without calling Claude.
- **Shared code** (`supabase/functions/_shared/`): the food catalog (with each food's section and usual pack size), the menu's shape and checks, the shopping list builder (`list.ts`), what each catalog food contains (`nutrition.ts`, for the numbers switch), the store rule (`stores.ts`), the picked products (`products.ts`: units of sale, the checks and the search text) and the pricing (`offers.ts`: the store rule on the picked products and the budget). Plain TS imported by the `chat` function and the web app, so both show the same numbers; `npm test` covers all of it.
- **Claude**: called only from Edge Functions, never from the browser. The system prompt lives in `supabase/functions/chat/prompt.ts`.
- **Price scraper** (`scraper/`, Python): a job run by hand from a dev machine ([ADR 0015](adr/0015-price-scraper-python-job-with-time-budget.md), [ADR 0018](adr/0018-gdu-listings-and-food-pages.md), [ADR 0023](adr/0023-scraper-prices-for-the-unit-of-sale.md)). It reads Ta-Ta's search API, and the Devoto, Géant and Disco sites' category and brand pages plus a few product pages per food, following [ADR 0008](adr/0008-how-we-read-supermarket-sites.md), and saves through Supabase's REST API with its own secret key.

## Data flow

1. Sign-in, either way:
   - Google: browser → Google's button → signed ID token → Supabase Auth (`signInWithIdToken`) → session, without leaving the page.
   - Email: browser → Supabase Auth → magic link email → back to the app with a session.
2. Chat: the browser creates a `conversations` row for a new chat, then → `chat` function (user token, conversation id) → Claude (streaming) → text streamed back to the browser. The function writes: `save_profile` calls write `profiles`, `save_menu` calls write `menus.data`, `update_shopping_list` calls write `menus.have`, and the new turns are appended to `messages`. When the stream ends, the browser reloads the chat's messages, so it sees the `save_menu` and `show_menu` calls it shows as previews, and the list calls it shows the list card under. It also reads the `menus` row then: the list card is drawn live from it, like the List tab, so only the last one shows, and once the list has been shown, a later turn that shows it again hides the menu previews it saved. A `show_menu` preview is the latest menu in the chat before it: a saved `save_menu` input or the server's `<saved_menu>` copy. A turn shows at most one `show_menu` preview, and none after a save in the same turn, because the model sometimes calls it right after `save_menu`.
3. Screens read `conversations`, `messages`, `profiles` and `menus` directly from Supabase, limited to the user's own rows. The List tab and the chat's list card build the list in the browser from `menus.data` and the catalog. The List tab writes `menus.have`, the only column of `menus` the browser may change. Both read the picked products from `store_products` (one query per store, `src/prices.ts`) and price what's left to buy, in the browser, with `offers.ts`.
4. Prices: `python -m scraper` → supermarket sites (1 request per second per site, 25 minutes at most) → `upsert_store_products` in batches → `store_products`, and `price_changes` through the trigger. One `scrape_runs` row per chain records how the run went.
